# Showcase notes

This file is for a human reviewer — a hiring manager, a Code with Claude submission reader, a Connectors Directory reviewer — who wants the fast version of "why this, why now" without reading the full README.

## Why this exists

This project is a direct response to a gap in Anthropic's own published guidance. The [Claude Cookbook's context-engineering guide](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools) documents three mitigations for context rot — tool-result clearing, compaction, and memory — but stops short of telling you *when* a given conversation actually needs one of them versus when it's still fine. Context Health Check is that missing diagnosis layer: a score, a reason for the score, and a recommendation that maps directly back to one of those three primitives.

## Shared-core architecture as evidence of intent

The repo ships three different front doors — a Chrome extension, an MCP server, and a static HTML demo — and every one of them imports the same `packages/core` scoring engine rather than carrying its own copy of the algorithm. That's a deliberate structural choice, not a default: it means a fix to the redundancy-detection threshold, or a new recommendation rule, only has to happen once and is guaranteed to be consistent across all three surfaces. `packages/core` has zero DOM or network dependencies and 55 passing Vitest tests covering token estimation, bloat detection, redundancy true/false positives, every score/grade boundary, and recommendation priority ordering — it's built to be the part every downstream consumer can trust without re-checking.

## Tradeoff decisions

1. **npm workspaces, not pnpm.** pnpm is faster and stricter about phantom dependencies — the more "correct" choice for a real monorepo. But this repo's primary audience is a stranger cloning it once to evaluate it, and npm ships with Node — `git clone && npm install && npm test` works with nothing extra to install. Reviewer friction mattered more here than marginal install-speed gains.

2. **Vitest, not Jest.** Native ESM/TS support with zero transform config, a Jest-compatible API so nothing about the tests looks unfamiliar, and it's the current default for new TypeScript packages.

3. **Char-heuristic token estimation by default; `gpt-tokenizer` and an Anthropic API key are both explicitly opt-in.** There's no offline tokenizer for Claude anymore, so an exact count means a network call — which conflicts with the product's actual promise ("nothing you paste leaves your browser by default"). The default has to work fully offline with zero keys; precision is a deliberate trade the user opts into, not a requirement.

   This produced a real bug worth naming, because it's the kind of thing that only shows up when you actually build and test the artifact rather than just design it: `gpt-tokenizer`'s vocabulary tables were originally re-exported from `packages/core`'s main entry point, which meant importing *anything* from core — even just `analyze()` — eagerly loaded the full BPE vocab into whatever bundled it. `packages/web-demo`'s single-file build came out to 4.3MB before this was caught, entirely from a token estimator the demo never uses. The fix was moving `GptTokenizerEstimator` to its own subpath export (`@context-health/core/gpt-tokenizer`), so the char-heuristic-only path — the actual default — stays small. The bundle is 44KB now.

4. **`ConversationAnalyzer.addTurn()` as the primary API, one-shot `analyze()` built on top of it.** The extension re-scores on every DOM mutation. Redundancy detection is pairwise (`O(n²)` in candidate turns) — recomputing it over the *entire* transcript on every mutation event would mean `O(n²)` work per event, `O(n³)` over a session's lifetime. `addTurn()` only compares the newly added turn against previously-cached shingle sets, so each new turn costs `O(n)` against existing candidates, not `O(n²)` against everything again. The side panel's own append-vs-replay logic (in `src/sidepanel/main.ts`) leans on this: appending new turns is the fast path; only an in-place edit to existing history triggers a full reset-and-replay.

5. **MV3 side panel, not a popup.** The product's entire value is glanceability while you're mid-conversation — a popup that closes the moment you click back into the chat defeats the point. The cost is real: the side panel and the content script run in separate execution contexts, so extracted turns cross via `chrome.runtime` message passing instead of direct DOM access from the panel's own script.

6. **Adapter pattern with mandatory paste-box fallback, not a best-effort selector.** claude.ai and chatgpt.com are React SPAs with class names that are not stable public API — they will drift. The build brief called this out as the single most likely failure mode of the whole extension, and it's treated that way in the code: `content-script.ts` degrades to a manual paste box the moment turn extraction returns nothing, rather than showing a blank or broken panel. This was smoke-tested directly (see commit history) — including deliberately breaking the adapter's selectors and confirming the panel falls back correctly instead of failing silently.

7. **`web-demo` bundles `core` into one static HTML file at build time**, rather than shipping an ES module import that needs a server to resolve. The demo's whole pitch is "open this file, no install, works on GitHub Pages or straight off disk" — that promise is about the *reader's* experience, so a build step for the maintainer is fine, but a runtime module-resolution requirement for the reader is not.

   This surfaced a second concrete bug: naively inlining the bundled JS into the HTML's `<script>` tag broke the page, because the HTML parser ends a `<script>` block on the literal byte sequence `</script` — even when it's inside a JS string. `gpt-tokenizer`'s vocabulary, trained on real scraped web text, happened to contain that exact sequence somewhere in its ~100k+ entries. The build script (`packages/web-demo/build.mjs`) now escapes any `</script` occurrence in the bundled output before inlining it. Both of these gpt-tokenizer issues were only found by actually building the artifact and loading it in a browser — which is why that step is part of the verification checklist for every package here, not just the core engine's unit tests.

8. **MCP server ships stdio-only in v1.** Stdio needs no hosting and is what makes `npx context-health-mcp` (once published) work directly in a Claude Desktop/Code config with zero setup. A remote, OAuth-authenticated version is a real scope increase — hosting, an auth server, discovery metadata — that only matters if this needs to be Connectors-Directory-listed or team-shared. That path is documented in [`packages/mcp-server/REMOTE.md`](packages/mcp-server/REMOTE.md) rather than built speculatively.

## What "done" looked like

Every package was built, typechecked, and either unit-tested (`core`) or exercised end-to-end before being committed — `web-demo`'s bundle was actually opened in a browser and scored against a known transcript, the MCP server's three tools were called through the real MCP Inspector CLI (not just typechecked), and the extension's settings panel and paste-box fallback pipeline were smoke-tested against the same scoring logic core's tests already cover. The one piece that couldn't be fully closed out in the same sitting the code was written — confirming the adapters' primary DOM selectors against a real, authenticated claude.ai/chatgpt.com session — is called out explicitly rather than asserted as done; see the extension's own commit message and the repo's `git log` for the follow-up.
